# מערכת ניהול לידים

מימוש של האפיון ב־[SPEC.md](./SPEC.md) כמנוע TypeScript ללא תלויות, שאינו קשור לתשתית מסוימת.
הגיליון / ה־DB, ספק ה־WhatsApp, ערוץ ההתראות והמודל מחוברים דרך ממשקים ב־`ports.ts`.

```bash
npm run test:leads     # node --test, ללא התקנות נוספות (Node 22.18+)
```

## מבנה

| קובץ | תפקיד |
|---|---|
| `schema.ts` | טבלאות Leads / Interactions וכל רשימות הערכים |
| `normalize.ts` | שלב 1 – נרמול WhatsApp / Instagram / טופס למבנה אחיד, נרמול טלפון ל־E.164 |
| `rules.ts` | כללים דטרמיניסטיים: תקינות, Opt-Out, התאמה, הסלמה, מעקב, חלון 24 שעות |
| `classifier.ts` | שלב 5 – פרומפט הסיווג ואימות פלט ה־JSON |
| `gemini-classifier.ts` | מימוש הסיווג עם Gemini (הספק שכבר בפרויקט) |
| `engine.ts` | `LeadsEngine` – שלושת הטריגרים ומדיניות השמירה |
| `access.ts` | תצוגה לפי תפקיד ודוח מצטבר למנהל |
| `memory.ts` | מימוש בזיכרון (כולל לוג גישה) – לבדיקות ולהדגמה |

## חיבור הטריגרים

| טריגר | קריאה |
|---|---|
| הודעה נכנסת (webhook אחד) | `engine.handleInbound(payload)` |
| שעתי | `engine.runHourlyScan()` – מעקבים + תזכורות יום לפני |
| `Lead_Status` → `נקבע תור` בגיליון / אירוע ביומן | `engine.onAppointmentBooked(leadId, dateIso, actor)` |
| יומי (מומלץ) | `engine.runRetention()` |

## החלטות מימוש (במקומות שהאפיון השאיר פתוח)

1. **סדר שלבים 4–5** – הסיווג רץ לפני איתור ההתאמה, כי "הטיפול המבוקש שונה" ידוע בוואטסאפ רק אחרי הסיווג. התוצאה זהה לאפיון.
2. **"סטטוס פתוח"** – גם `דורש בדיקה` ו־`נקבע תור` נחשבים פתוחים לצורך צירוף הודעה, כדי שלקוחה עם תור שכותבת "אפשר להזיז?" לא תקבל ליד חדש והודעת פתיחה.
3. **אי־התאמה בטיפול** – "לא ידוע" לא נחשב טיפול שונה.
4. **Opt-Out לפי טלפון** – החסימה חלה על כל הלידים של המספר. פנייה חדשה ממספר חסום נפתחת כליד `מזכירה` בלי שום שליחה אוטומטית. תור שכבר נקבע לא נסגר בגלל הסרה – רק ההודעות נעצרות.
5. **זיהוי Opt-Out** – ביטויים מפורשים בלבד: "הסרת שיער" / "הסרת קעקוע" הם טיפולים ולא בקשת הסרה.
6. **הסלמה נאכפת בקוד** – מעבר לפלט ה־AI יש רשת מילות מפתח (רפואי / תלונה / ביטול-החזר / הנחה) שיכולה רק להוסיף הסלמה. ביטחון מתחת ל־0.7, JSON לא תקין או שגיאת מודל → `AI לא בטוח`.
7. **טקסטים ללקוח קבועים** – הודעות הפתיחה, ההמתנה, המעקב והתזכורת הן תבניות מתוך `config.texts`. ה־AI לא מנסח הודעות ללקוח, כך שאין דרך שיופיעו בהן מחיר או מידע רפואי.
8. **מעקב** – רק כש־`Handling_Mode = AI` (ליד שהוסלם לא מקבל תזכורות אוטומטיות). תגובה של הלקוח מאפסת את ספירת הניסיונות. אחרי 2 ניסיונות ועוד 24 שעות בלי מענה → `נסגר – לא ענה`.
9. **חלון 24 שעות** – בתוך החלון נשלח טקסט; מחוצה לו רק תבנית מאושרת (`config.templates`). אין תבנית → לא נשלח דבר והמזכירה מקבלת התראה. ליד מטופס לא פתח חלון, לכן הפנייה אליו תמיד בתבנית.
10. **הסכמה** – טופס בלי checkbox: מקבל תגובה ראשונית (כמו באפיון), אבל לא מעקבים.
11. **תוכן רפואי** – שורת Interactions של הודעה שהוסלמה כרפואית מסומנת `Sensitive`; המזכירה רואה אותה מוסתרת והצוות הרפואי רואה אותה במלואה. סיכום ה־AI לא נשמר ב־Notes במקרה כזה.
12. **שמירה** – לידים סגורים שלא עודכנו 12 חודשים: ההתכתבויות נמחקות, והליד נמחק או מוסתר (`retention.mode`). רשומת Opt-Out נשמרת תמיד במינימום (טלפון + דגל) כדי שהחסימה תמשיך לחול.
13. **ההתראה לא יכולה להכיל תוכן** – לטיפוס `StaffNotification` אין שדה לתוכן ההודעה.

## מה עוד חסר לפריסה

- מימוש `LeadRepository` / `InteractionRepository` מעל Google Sheets / Airtable / DB, עם לוג הגישה (החוזה ב־`memory.ts`).
- מימוש `Messenger` מול ספק ה־WhatsApp (ו־Instagram, כולל מיפוי מזהה המשתמש בערוץ), ורישום התבניות אצל הספק.
- מימוש `Notifier` (למשל קבוצת WhatsApp פנימית / Slack / מייל).
- endpoint ל־webhook ותזמון לסריקה השעתית (Cloud Function / Make / n8n).
- אימות מול עו"ד פרטיות של מדיניות השמירה והיקף ההסכמה.
